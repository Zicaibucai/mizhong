# 全站语言同步

中文是唯一母版。管理员只维护中文，其余十种语言由 DeepSeek 生成、随发布一起上线。

这份文档写给**要把它部署上线、以及之后要维护它的人**。设计取舍写在对应源码的注释里，
这里只讲「怎么用、怎么上线、出问题怎么办」。

---

## 1. 一次编辑的完整流程

```
管理员改中文
   │
   ├─ 保存 ──────────► 写进草稿（Product.draftData / Page.draftData）
   │                    访客看不到任何变化
   │
   ├─ 点「一键翻译」 ─► 把中文改动翻译成 10 种语言，也写进草稿
   │                    （可选：不点也行，发布时会自动补）
   │
   └─ 点「发布」 ────► 1. 校验
                      2. **同步保险**：把还没翻的语言补齐
                      3. 全部语言都成功 → 一次写入线上 + 留一版快照
                         任何一个语言失败 → **放弃发布**，线上保持原样
```

「发布必须自带同步保险」是这套东西的核心：管理员不需要记得先点翻译。
即使忘了，发布也会把最新的中文补翻到全部语言，然后一起上线。

## 2. 可翻译的内容与字段

路由在 `src/lib/translation/adapters.ts`，每种内容类型一个适配器。
加一种内容类型只需要在那里加一个适配器，其余（同步中心、发布保险、命令行）自动认得它。

| 内容类型 | 字段 | 说明 |
| --- | --- | --- |
| **商品** | 名称、一句话介绍、完整介绍、尺寸摘要、规格说明、应用场景、SEO 标题、SEO 描述 | 8 个直接字段 |
| | 规格表列名、规格表单元格（按行 id + 列 id） | 管理员自由增删行列 |
| | 型号/颜色选项组名称、选项名称 | |
| | 旧版「参数」的名称与值 | 兼容 specTable 出现之前的数据 |
| **页面**（含首页） | 页面标题、SEO 标题、SEO 描述 | |
| | 每个区块的标题、副标题、正文、按钮文字 | 按钮的**链接**不翻，见下 |
| **公司资料** | 公司名称、标语、公司介绍、定位、地址、营业时间、SEO 标题、SEO 描述 | |
| **联系方式** | label（「销售咨询」这类说明文字） | 地址类型额外翻 `value`，见下 |
| **导航** | 导航文字 | |
| **商品类目** | 类目名称、类目说明 | |
| **素材** | 图片标题、图片说明、alt 替代文字 | |

### 刻意不翻的字段，以及为什么

| 字段 | 原因 |
| --- | --- |
| 所有 slug | 它是网址，不是文案。翻它等于把页面挪走。改 slug 会 301，见第 6 节 |
| 区块的 `ctaHref`（按钮链接） | 链接是结构。前台渲染时由 `withLocale` 补当前语言前缀，翻它只会翻出 404 |
| 图片/视频的 key、url | 路径 |
| 价格、货币、计价单位、起订量、SKU、型号代码 | 数字与代号。提示词要求原样保留，但更好的是根本不发出去 |
| 联系方式里非地址类型的 `value` | 电话、邮箱、WhatsApp 号、微信号 —— 翻它们最好的结果是原样返回，最坏的结果是打不通 |
| 商品是否推荐、排序、开关、分类归属 | 配置 |
| 后台界面、前台固定文案 | 那些在 `src/lib/i18n/dictionaries/` 与 `catalog.ts` 里，本来就已是 11 种语言，不走 DeepSeek |

如果哪天要让某个「结构字段」也参与翻译，改 `adapters.ts` 里对应的 `readSource`
即可 —— 但先想清楚它是不是真的该翻。

## 3. 同步是怎么判定「要不要翻」的

每个「内容 × 语言」在 `TranslationState` 里有一行，逐字段记着**翻译当时中文的哈希**。

- 中文没变 → 哈希对得上 → 不重翻，**一个请求都不发**；
- 中文改了 → 只有那几个字段哈希对不上 → **只翻那几个字段**；
- 中文清空 → 该字段从文档里消失 → 译文被清掉，**不调用模型**；
- 中文没变、别的字段变了 → 那几个字段的哈希没动 → 已翻好的译文**原样保留**。

「过期没过期」是每次读的时候现场算的，不是存下来的。存一份 STALE 标记意味着
「中文一改就要记得把标记写对」，而写中文的入口有很多（后台各页面、将来的批量导入、
直接改库）—— 漏掉一处，那个字段就会永远显示「已同步」，实际停在旧版本上。
这类 bug 不报错，只让某几种语言的译文悄悄过期。

### 已有的译文不会被覆盖

首页、公司资料、导航在功能上线前**已经有手写的英文与越南语内容**。这些内容的字段
没有哈希记录，机器无法判断它们是否与当前中文一致。规则是**认下来、不覆盖**
（需求 6.7 要求保留人工调整过的译文），同时补上哈希 —— 这样中文以后再改，
它们就会正确地变成「待同步」。

代价是：如果中文在这次上线**之前**就改过、旧译文没跟着改，机器判断不出来。
这种情况用同步中心的「**重新翻译全部语言**」按钮 —— 它会连已同步的字段一起重生成，
**会覆盖人工写过的措辞**，所以要点确认，只在你确信译文有问题时用。

回滚历史版本、删除内容时会**清掉**同步状态（`invalidateTranslationState`）：
内容整体换掉了却没经过翻译引擎，不清的话记录会描述一个已经不存在的版本。
回滚后那一版快照里的译文与那一版中文是配套的，所以下一次同步会把它们重新认下来。

## 4. 长任务

首页与全站内容的翻译可能远超单个 Server Action 的时限，所以任务与每个工作项的状态
落在数据库（`TranslationJob` / `TranslationJobItem`），每次推进只跑一段预算
（后台 15~20 秒，命令行 20 秒），远低于 60 秒上限。

- **断点就是工作项自己的状态**（PENDING / SYNCED / FAILED / SKIPPED），不另记游标。
  少一份需要维护、又可能与事实对不上的状态。
- **幂等键**带上中文版本号：同一次发布的重复点击命中同一个任务。
- **并发锁**是一把会超时的 `lockedAt`：取锁失败的调用方直接返回当前进度，
  进程被杀不会让任务卡死在 RUNNING 上。
- **收尾时再算一次计划**：工作项说「都成功了」不等于内容真的同步了 ——
  同步过程中有人改了中文的话，已翻好的字段会重新变成待同步，任务会以
  `PARTIAL` 结束并带上 `source-changed`，发布随之失败。

## 4.5 应急发布（DeepSeek 故障时的兜底）

翻译服务挂掉时，管理员会遇到一个死结：改了一个错别字，却因为译文补不齐而发不出去。
「应急发布中文，其他语言稍后同步」就是为这个场景准备的 —— **它是兜底，不是常规出口**。

### 什么时候才会出现

**默认不显示。** 只有发布时真的尝试过自动翻译、并且失败原因属于「服务暂时不可用」
才会出现：超时、网络错误、429、DeepSeek 5xx。

这些情况**不会**出现应急发布，界面会告诉你下一步该做什么：

| 失败原因 | 为什么不给应急 | 该怎么办 |
| --- | --- | --- |
| 没配 Key / Key 被拒 | 是配置问题，修它只要十秒 | 去「翻译设置」填 Key |
| 返回结构不对 | 属于数据结构错误 | 重试；反复失败要查模型或提示词 |
| 模型漏翻字段 | 同上 | 重试 |
| 中文同步途中被改过 | 内容一致性问题 | 再点一次发布 |
| 内容校验不过（slug、封面、标题…） | 应急绕过的是翻译，不是内容规范 | 按提示补齐 |

服务端会**自己重试一次翻译**再判定，不采信客户端的说法 —— 否则改一个请求就能绕过。

### 它做了什么

1. 只把**中文**写上线；
2. **已有的外语原样保留**，继续显示各自上一次成功发布的版本，一个字段都不会被清空；
3. 没有译文的语言仍然没有 —— 不生成假的翻译行、不进 hreflang、不进 sitemap；
4. 这些语言被标记为**待同步**，而**不是伪造「已同步」**：不写任何来源哈希，
   也不推进中文版本号；
5. 写一条**独立的发布记录**（`kind = EMERGENCY`），带着操作人、原因、
   翻译失败类型、中文 sourceRevision、以及哪些语言停在旧版 / 仍然缺失，
   同时记一条同样内容的审计日志（不含 Key、原文与译文）；
6. 后台**每一页**顶部常驻一条「多语言待同步」的警告，直到补齐为止。

### 故障恢复

应急发布会自动排一个**补齐任务**，并把它钉在**刚刚发布的那一版中文**上
（`sourceHash`）。之后：

- 翻译服务恢复后任务会自动跑完，**不需要人工逐语言审核**；
- 跑完自动发布一次「语言补齐版本」（`kind = FULL`），警告随之消失，
  hreflang 与 sitemap 也跟着更新；
- 页面上的「立即重试」按钮可以手动催一次，走的是同一个任务；
- **中文在故障期间又改过的话，旧任务整批作废**（工作项标记 `source-changed`），
  一个字段都不会写回去 —— 旧译文覆盖新内容是最难查的一类错乱。

## 5. 上线顺序（**不要打乱**）

### 第一阶段：部署功能，不动生产内容

```bash
cd /opt/mizhong
git pull --ff-only origin main
npm ci
# Prisma CLI 读 .env 而项目用 .env.local，必须先取值再注入
DBURL=$(grep "^DATABASE_URL=" .env.local | cut -d= -f2- | sed "s/?schema=public//") \
  && DATABASE_URL="$DBURL" npx prisma migrate deploy

# ⚠️ 必须先停服务再构建 —— 原因见下面的「部署顺序」小节
pm2 stop mizhong-web
rm -rf .next
npm run build
pm2 start mizhong-web
pm2 save
```

> **部署顺序（2026-09-18 线上踩到，别再踩）**
>
> 构建期间**旧进程不能还活着**。`npm run build` 会重建 `.next`，而旧进程仍在用
> **旧代码**响应请求；这些请求会触发 ISR 重新生成，把**旧代码渲染出来的页面**
> 写进刚构建好的 `.next`。之后 `x-nextjs-cache: HIT` 端出来的就是那份被污染的产物。
>
> 症状很有迷惑性：**部署了、也 reload 了，页面却还是旧的**，看起来像缓存没清，
> 其实是上一版代码写的预渲染。2026-09-18 就因为这个，前台连着几次拿到的都是
> 部署前的数据（页脚显示的是早已改掉的邮箱）。
>
> 做成 `stop → rm -rf .next → build → start` 之后，构建期间没有任何进程能写入，
> 产物就是干净的。代价是约 30 秒停机。
>
> 另外：`Cache-Control` 里带 `stale-while-revalidate=31535940`，所以 60 秒窗口
> 过期后的**第一次**请求仍然返回旧页面，后台再生成，**第二次**才是新的。
> 部署后立刻验证要看两次，否则会误判成「没生效」。

这一阶段的迁移是**纯新增**（新表、可空列、新枚举），对现有数据零影响。

在服务器的 `.env.local` 里**明确写上**：

```
STRICT_LOCALE_FALLBACK=false
```

不写也是关的（只有严格等于 `true` 才开启），但明确写出来有两个好处：
下次有人翻到这个文件时不会去猜它现在是什么状态；也不会因为别人顺手加了
`STRICT_LOCALE_FALLBACK=1` 之类「看起来也对」的写法而产生误解。

部署后先确认：

```bash
npm run translation:sync status
```

它会只读地列出还差多少，**不发请求也不写库**。

> **注意**：部署之后，编辑并发布任何一条内容都会要求它的全部语言都是最新的。
> 对只有中文的正式商品来说，这意味着第一次发布时会真的调用 DeepSeek。
> 这是设计如此（发布自带同步保险），不是故障。

### 第二阶段：生产数据库备份 + 首次全站同步

```bash
# 1. 备份并验证（备份文件非空、能被 pg_restore 认出）
mkdir -p /opt/mizhong-data/backups
DBURL=$(grep "^DATABASE_URL=" .env.local | cut -d= -f2- | sed "s/?schema=public//")
STAMP=$(date +%Y%m%d-%H%M%S)
pg_dump "$DBURL" -Fc -f /opt/mizhong-data/backups/mizhong-$STAMP.dump
ls -l /opt/mizhong-data/backups/mizhong-$STAMP.dump
pg_restore --list /opt/mizhong-data/backups/mizhong-$STAMP.dump | head

# 2. 盘点
npm run translation:sync status

# 3. 先同步一条，确认 Key、模型、写入都正常
npm run translation:sync sync --limit 1

# 4. 单条成功后跑剩下的
npm run translation:sync sync
```

单条跑完后做**程序化**验证即可，不要求逐句人工审核：结构、URL、SEO、
占位符、发布状态都能用脚本查（见第 8 节）。

同步**不碰中文原文** —— 它只读中文、只写其它语言。
记录四个数字：成功、失败、跳过，以及**保留已有 en/vi 的数量**（首页、公司资料、导航
里本来就有手写英文与越南语，它们会被认下来而不是重翻）。

任意内容失败时：线上保持当前版本不变，用 `npm run translation:sync retry` 只重试失败项。

后台 `/admin/sync` 是同一件事的图形入口：能看进度、只重试失败的、查看错误。
两者驱动的是同一个任务引擎，用哪个都行；命令行适合首次全量（不依赖浏览器开着）。

### 第三阶段：验证，然后开启严格回退

```bash
# 逐语言抽查商品与首页，确认内容、SEO、hreflang 都对
curl -sI https://htd123.com/ar/products/tehsugouzi | head -1
curl -sI https://htd123.com/ja/products/manli | head -1
```

**只有下面五条全部满足才能开启**：

1. `tehsugouzi` 与 `manli` 已经拥有全部目标语言；
2. 首页、公司资料、导航、联系方式、素材都已完成同步；
3. 每一条需要公开的语言内容都有成功的发布版本（`/admin/sync` 上没有「待同步」）；
4. 那 20 个外语商品 URL 在严格模式下仍然返回 200；
5. hreflang、canonical、metadata 与 sitemap 验证通过。

确认之后，在服务器的 `.env.local` 里加：

```
STRICT_LOCALE_FALLBACK=true
```

**只有严格等于 `true` 才开启** —— `1`、`TRUE`、`yes` 一律无效。这是刻意的：
这个开关一打开，没有自己译文的 URL 会直接 404，一个拼写差异的代价太大。

然后 `pm2 reload mizhong-web --update-env && pm2 save`。**不需要重新构建。**

开启后的三条规则，回答的是两个不同的问题：

- **渲染**：中文页面只认中文；其它语言先看该语言，没有则回退英文；
  该语言与英文都没有则 404。
- **hreflang 与 sitemap**：**只列有自己译文的语言**。一个显示英文内容的阿拉伯语
  页面，在 hreflang 里声明自己是阿拉伯语，等于告诉搜索引擎「这里是阿拉伯语内容」——
  比不声明更糟。

**开启前一定先确认同步已完成。** 否则「只有中文的商品 × 10 种语言」这些原本
返回 200 的地址会一起变成 404。有疑问就先跑一次 `translation:sync status`。

## 6. 回滚

### 回滚代码

```bash
cd /opt/mizhong
git log --oneline -5          # 找到上一个稳定的提交
git checkout <上一个提交>
npm ci && npm run build && pm2 reload mizhong-web --update-env
```

**数据库不用回滚**：这一版迁移全是新增，旧代码不认识新表但也不会被它们影响。
真要回滚数据，用第二阶段的备份：

```bash
pg_restore -d "$DBURL" --clean --if-exists /opt/mizhong-data/backups/mizhong-<时间戳>.dump
```

### 回滚单条内容

后台的内容版本（商品编辑器与页面编辑器的「版本历史」）里点「恢复」——
它把该版本写回**草稿**（中文与全部语言一起），确认无误再点发布。
线上内容全程不受影响，误点也能再退回去。最多保留三个版本。

### 撤销一次应急发布

应急发布的内容已经上线，没法「撤销」—— 但它留下的是一次正常的发布版本：
在编辑器的「版本历史」里恢复到应急发布之前的那一版，确认后发布即可。
外语从来没有被动过，所以恢复中文不会影响它们。

### 关闭严格回退

把 `STRICT_LOCALE_FALLBACK` 删掉或设为 `false`，`pm2 reload mizhong-web --update-env`。
立刻回到旧行为。

## 7. 安全约定

- **API Key 只存在于服务端。** 数据库里以 AES-256-GCM 加密存储（`v1.` 前缀），
  传给浏览器的一律是 `maskApiKey()` 的结果。
- **`TRANSLATION_ENCRYPTION_KEY` 不进 Git、不进日志、不进构建产物。**
  它只从环境变量读。改动它会导致已存的 Key 解不开 —— 后台会明确显示
  「无法解密」并**停用翻译**，而不是拿半截垃圾去发请求。
- **日志里没有 Key、没有原文、没有译文全文。** 只有错误类别、条数、耗时、token 估算。
- 每个同步动作都校验管理员会话（`requireAdminOrError`），并保留原有的
  每分钟 10 次 / 并发 2 的限流；全站任务另有一把幂等锁。
- 失败的提示会明确区分「没配 Key」与「模型那边出错」—— 前者要去翻译设置填 Key，
  后者只能等一会儿再试，让管理员知道该做什么。

## 8. 常用命令

```bash
npm run translation:sync status                    # 只读盘点（不发请求、不写库）
npm run translation:sync sync                      # 同步全部已发布的中文内容
npm run translation:sync sync --limit 5            # 先试 5 条
npm run translation:sync sync --type product --id <商品id>
npm run translation:sync retry                     # 只重试最近一次任务里失败的
```

后台入口：`/admin/sync`（语言同步）、`/admin/settings/translation`（DeepSeek 配置）。
